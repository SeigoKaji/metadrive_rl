# 固定経路の定義と構築

この文書は、[観測入力と報酬関数の仕様](methods.md) の 1.2 節「固定経路を作る」の
補足です。道路の通過順序、車線の選択、接続の検証、累積距離による表現を説明します。

ここでいう **固定経路** は、**Navigation が決めた道路の順序に沿って、開始時の
車線番号に対応する車線の中心線をつなぎ、接続を確認できた範囲を保持した基準線**です。
この基準線上の位置を、「始点から中心線に沿って何 m 進んだか」という累積距離
$S$ で表します。

## 1. 通過する道路の順序

元になるのは、車両の `Navigation.checkpoints` です。これは道路ネットワーク上の
ノードを通過する順序を持っています。たとえば、

```python
checkpoints = ["A", "B", "C", "D"]
```

なら、計画された有向道路は次の 3 本です。

$$
A \rightarrow B,\qquad B \rightarrow C,\qquad C \rightarrow D.
$$

`A` や `B` は道路ネットワーク上の識別子です。各道路に属する車線の情報は、
次のように取得します。

```python
navigation.map.road_network.graph["A"]["B"]
```

この値には、`A → B` 方向の道路にある複数の Lane オブジェクトが入っています。
「有向」は、道路をどちら向きに通るかも含むという意味です。

道路の通過順序は Navigation が決定します。参照している MetaDrive の
`NodeNetworkNavigation` では、`shortest_path()` が幅優先探索を使い、道路の接続数を
基準とした経路を求めています。lookahead 側は、その計画結果から具体的な車線の
中心線を取り出します。

実装では、[adapter.py](../adapter.py) の `_navigation_context()` が
`checkpoints` の隣り合うノードを組にし、`_navigation_edge_lanes()` が
`graph[start][end]` から各道路の車線を読み取ります。

## 2. 各道路から開始時と同じ番号の車線を選ぶ

MetaDrive の車線は、次のようなインデックスで識別されます。

```python
lane.index = (開始ノード, 終了ノード, 道路内の車線番号)
```

たとえば reset 時の車線が `("A", "B", 1)` だった場合、開始車線番号として `1` を
保持します。その後、計画経路上の各道路から、この番号に一致する車線を 1 本ずつ
選びます。

| 計画された道路 | 道路内の車線番号 | 選択する候補 |
|---|---|---|
| `A → B` | `0, 1, 2` | `("A", "B", 1)` |
| `B → C` | `0, 1, 2` | `("B", "C", 1)` |
| `C → D` | `0, 1, 2` | `("C", "D", 1)` |

このように、経路を構成する候補の列は、

$$
\mathrm{Lane}(A,B,1)
\rightarrow \mathrm{Lane}(B,C,1)
\rightarrow \mathrm{Lane}(C,D,1)
$$

となります。車線番号は各道路内の番号なので、道路が変われば別の Lane
オブジェクトになります。この段階では候補を選んだだけであり、後述する接続の
検証に通った区間を固定経路へ採用します。

このプロジェクトの `StartLaneMetaDriveEnv` は、開始車線を目標とする設定が有効な場合、
reset 時の番号を `_target_lane_ordinals` に記録します。
`_saved_start_lane_ordinal()` はこの保存値を優先して読み取ります。
保存された開始車線番号を持たない環境では、reset 直後の `vehicle.lane_index` の
末尾から番号を取得します。

該当する番号の車線がない場合や、同じ番号の車線が複数あって一つに定まらない場合は、
その道路の手前で経路を打ち切ります。

保存処理は [start_lane_env.py](../../start_lane_env.py) の `_get_reset_return()`、
番号の読み取りと候補の選択は [adapter.py](../adapter.py) にあります。

## 3. 1 区間は、1 つの Lane の中心線全体

固定経路の **区間** は、**1 つの Lane オブジェクトが表す車線の、始点から終点までの
中心線**に対応します。

Lane 上の位置は、次の呼び出しで求めます。

```python
lane.position(s, 0.0)
```

- `s`：その Lane の始点から、車線に沿って進んだ距離 [m]
- `0.0`：中心線からの横方向のずれ [m]。ゼロなので中心線上の点になる

使用する範囲は、$0 \leq s \leq \mathrm{lane.length}$ です。
現在の MetaDrive 用 adapter が対応する形状は次の 2 種類です。

| Lane の種類 | 中心線の形状 | 区間の長さ |
|---|---|---|
| `StraightLane` | 始点と終点を結ぶ直線 | 始点と終点の距離 |
| `CircularLane` | 指定された中心・半径・回転方向を持つ円弧 | 半径 × 円弧の角度 [rad] |

たとえば半径 $10\,\mathrm{m}$ の 90 度カーブなら、その区間の長さは、

$$
\ell = 10 \times \frac{\pi}{2}
\approx 15.71\,\mathrm{m}
$$

です。円弧に沿って測るこの長さを **弧長** と呼びます。

経路上の座標は Lane の幾何計算から求めます。
[geometry.py](../geometry.py) の `ReferencePath.position_at()` は、
指定された累積距離に対応する Lane を選び、その `position(s, 0.0)` を呼び出します。

## 4. 車線同士の接続を検証する

### 4.1 接続端点・接線・車線数・幅

同じ車線番号を持つ Lane を選んだあと、隣り合う区間の接続を検証します。
現在の既定値での条件は次のとおりです。

| 確認するもの | 比較する内容 | 許容条件 |
|---|---|---|
| **接続端点** | 前の中心線の終点と、次の中心線の始点 | 距離が **0.001 m 以下** |
| **接線方向** | 前の終点での進行方向と、次の始点での進行方向 | 角度差が **0.001 rad 以下**（約 0.057 度） |
| **車線数** | 前後の有向道路に属する車線の本数 | 同じ本数 |
| **車線幅** | 前後の車線幅 | 差が **0.001 m 以下** |

たとえば端点については、次の 2 点の直線距離を比較します。

```python
previous_lane.position(previous_lane.length, 0.0)
next_lane.position(0.0, 0.0)
```

接線方向は、その点で中心線に沿って前へ進む向きです。
`heading_theta_at()` から前の終点と次の始点の向きを読み取り、角度の周期を考慮して
差を比較します。直線と円弧でも、接続位置と進行方向がそろい、ほかの条件も
満たせば接続できます。

車線そのものについても、対応する種類であること、長さが正で有限であること、
幅が正で有限であることなどを確認します。各 Lane の始点と終点の幅の差も、
既定値では 0.001 m 以下である必要があります。

車線情報は [adapter.py](../adapter.py) の `_lane_descriptor()` が取得し、
接続の測定と検証は [geometry.py](../geometry.py) の `connection_measurement()` と
`build_reference_route()` が行います。

### 4.2 別車線も含めて、接続先が一つに定まることを確認する

接続の検査では、**次の計画済み道路にある全車線**を調べます。
採用条件は、**接続条件を満たす車線が 1 本だけ存在し、その車線が、開始車線番号で
選んだ候補と一致すること**です。

開始車線番号が `1` の場合、次のように扱います。

| 次の計画済み道路での接続状況 | 扱い |
|---|---|
| 番号 `1` の車線だけが接続条件を満たす | 採用する |
| 番号 `1` と番号 `2` の両方が接続条件を満たす | 接続先が曖昧なので打ち切る（`ambiguous_successor`） |
| 番号 `2` だけが接続条件を満たす | 開始車線番号の連続性を満たせないので打ち切る（`start_lane_ordinal_not_continuous`） |
| 接続条件を満たす車線がない | 端点・接線・車線数・幅などの検証で打ち切る |

次の道路に、種類や幅などを検査できない車線がある場合も、接続先を確実に検証
できない境界として扱います。

ここで調べる候補の範囲は、Navigation が次に通ると決めた道路上の車線です。
この一意性の検証は [adapter.py](../adapter.py) の `_navigation_context()` が行います。

### 4.3 打ち切るときは、検証済みの先頭部分を残す

たとえば最初の 2 区間は接続できても、その先の区間との接続を検証できない場合、
固定経路に採用するのは最初の 2 区間です。2 番目の区間の終点を固定経路の終端とします。

![直線と円弧を接続し、検証できない境界までを固定経路とする模式図](assets/lookahead_path.svg)

したがって、固定経路の終端は Navigation の目的地より手前になる場合があります。
実装は `boundary_reason` に打ち切り理由を保持します。
すべての計画区間を採用できた場合は `route_end`、最初の区間から採用できなければ
固定経路は空になります。

`build_fixed_navigation_route()` が、検証済みの経路と打ち切り理由をまとめた
`RouteBuildResult` を返します。

## 5. 累積距離 S で経路全体を表す

### 5.1 Lane 内の距離と、経路全体の距離

採用した区間数を $m$、区間番号を $i=0,1,\ldots,m-1$ とします。
各区間の長さを $\ell_i$ [m] とすると、区間 $i$ の始点までの累積距離は、

$$
S_i = \sum_{j=0}^{i-1}\ell_j,\qquad S_0=0
$$

です。空の和は 0 とします。固定経路の全長は、

$$
S_{\mathrm{end}}=\sum_{i=0}^{m-1}\ell_i
$$

になります。ここで $i$ は経路上の区間番号であり、各道路内の車線番号とは別の番号です。

経路上の累積距離 $S$ が区間 $i$ にある場合、その Lane 内の距離は $S-S_i$ です。
その位置の world 座標を、

$$
\boxed{
P(S)=\mathrm{Lane}_i.\mathrm{position}(S-S_i,\ 0)
}
$$

で求めます。$P(S)$ は地図上の共通座標系における 2 次元の点です。
空でない固定経路の定義域は $0\leq S\leq S_{\mathrm{end}}$ です。

つまり、**経路全体の距離から、それ以前の区間の長さを引き、その Lane 内の距離に
変換する**仕組みです。

### 5.2 数値例

20 m の直線に、半径 10 m・90 度の円弧をつないだ場合は、次のようになります。

| 区間 | 長さ | 経路全体での累積距離 |
|---|---|---|
| 最初の直線 | 20 m | 0〜20 m |
| 次の円弧 | 約 15.71 m | 20〜約 35.71 m |

この経路で $P(24)$ を求める場合、$24-20=4\,\mathrm{m}$ なので、
円弧の始点から 4 m 進んだ中心線上の点を返します。

**$S=0$ は、最初に採用した Lane の始点です。** 車両がその 5 m 先の中心線上に
スポーンしたなら、reset 直後の投影位置も $S_{\mathrm{proj},0}=5\,\mathrm{m}$ になります。
累積距離の原点は、この Lane の始点に固定されています。

車体が中心線から横にずれている場合、その横方向の距離は $S$ に加えません。
投影点を選ぶ処理の詳細は、[methods.md](methods.md) の 1.3 節
「車体基準点と投影」を参照してください。

[geometry.py](../geometry.py) の `build_reference_route()` が各区間の `start_s` と
`end_s` を累積して保存し、`ReferencePath` が経路上の位置を取得する機能を持ちます。

## 6. 経路を保持し、各 step で注視点を求める

### 6.1 エピソード中の固定経路

元の環境の reset が終わった直後に、`MetaDrivePreviewProvider.reset()` が経路を
一度構築し、`MetaDrivePreviewProvider._route` に保持します。
次のエピソードの reset では、そのエピソードの Navigation と開始車線番号から
経路を作り直します。

車両が横にずれたり車線変更したりしても、参照する経路は reset 時に構築したものを
使います。エピソード中に `Navigation.checkpoints` が変わった場合は
`navigation_route_changed` として注視点を無効にします。
保存された開始車線番号の変更を検出した場合も、注視点を無効にします。

このライフサイクルは [env.py](../env.py) の `LookaheadEnv.reset()` と
[adapter.py](../adapter.py) の `MetaDrivePreviewProvider` が管理します。

### 6.2 注視点は固定経路の上を進む

行動ステップを $t$、注視距離を $L_d$ [m] とします。
各 step では、車両の位置から次の処理を行います。

1. 車体基準点を固定経路へ投影し、対応する累積距離 $S_{\mathrm{proj},t}$ を求める。
2. そこから注視距離 $L_d$ だけ進み、累積距離 $S_{\mathrm{goal},t}$ を求める。
3. その位置の world 座標を注視点 $q_t$ にする。

$$
\begin{aligned}
S_{\mathrm{goal},t} &= S_{\mathrm{proj},t}+L_d,\\
q_t &= P\!\left(S_{\mathrm{goal},t}\right).
\end{aligned}
$$

たとえば $S_{\mathrm{proj},t}=24\,\mathrm{m}$、`lookahead_m = 6.0` なら、
注視点は $P(30)$ です。前節の例では、円弧の始点から 10 m 進んだ点になります。
この 6 m は中心線に沿って測ります。

経路全体の長さは、採用した Lane の長さの合計で決まります。
`lookahead_m` は、その経路上でどれだけ先を見るかを指定します。

$S_{\mathrm{goal},t}>S_{\mathrm{end}}$ の場合は、注視点を無効にします。
終端へ注視点を縮めたり、終端の先へ中心線を延長したりする処理は行いません。
投影先の曖昧さなどを含む注視点の有効判定全体は、[methods.md](methods.md) の
1.3〜1.6 節を参照してください。

投影と注視点の計算は [geometry.py](../geometry.py) の `project_to_path()` と
`compute_preview()` が行います。

## まとめ

この実装の固定経路は、**計画済みの道路順序と開始車線番号から選んだ、接続を
検証済みの車線中心線の列**です。
その列を累積距離で扱えるようにしたものが `ReferencePath` であり、
`ReferencePath.position_at(S)` が文書の $P(S)$ に対応します。
各 step では、この固定経路へ車体基準点を投影し、経路に沿った前方の注視点を求めます。
